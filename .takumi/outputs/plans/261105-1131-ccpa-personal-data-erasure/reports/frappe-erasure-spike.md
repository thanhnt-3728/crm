# Frappe erasure spike (phase 03 step 1, 2026-11-05)

Bench: `crmtest-frappe`, site `test_site`, frappe 16.55.2 (version-16 @3d1284c), crm develop, whatsapp develop.
Script: a throwaway lead plus File and Communication rows, then cleaned up (rows deleted and committed, disk file removed).

| # | Question | Result | Consequence for phase 03 |
|---|---|---|---|
| 1 | Does `delete_doc("File", n, delete_permanently=True, ignore_permissions=True)` remove the disk file? | **Only when `content_hash` is set.** `File.on_trash` registers `_delete_file_on_disk` as an after-commit hook, and that hook deletes only when `self.content_hash` is set and no other File row has the same hash. A row without a hash (older uploads, raw inserts) keeps its disk file: `disk_file_exists_after_commit_no_hash: true`. A real upload with a hash is removed after the commit. | The job does not use `delete_doc` for files. `post_commit.delete_files` deletes the File row raw and the disk file itself (`frappe.utils.file_manager.delete_file`, missing files ignored), one commit per file. It keeps the disk file when an unmatched File row shares its `file_url` (`shared_files.file_url_is_shared`). |
| 1b | Side effects of `delete_doc` on File | `on_trash` adds an **"Attachment Removed" Comment** to the record the file was attached to, with `content` set to the file name (`erasure-spike.txt`). `delete_permanently=True` writes no Deleted Document (confirmed). | That would leave a new comment on her Lead after the erasure, naming her file (e.g. `marisol-portrait.png`). Using raw deletion avoids it. |
| 2 | Does `frappe.db.set_value(..., update_modified=False)` on a `track_changes` doctype (CRM Lead, `track_changes=1`) write a Version? | **No Version row** (`version_rows_added_by_set_value: 0`), and `modified` is unchanged. | All executor writes use `frappe.db.set_value(..., update_modified=False)` and `frappe.db.delete`. `test_hidden_copies.test_no_new_versions` runs with `frappe.in_test` patched to False, plus a control `doc.save()` that does create a Version. |
| 3 | Does a Communication linked to her Lead write a snippet into the parent's `_comments`? | **No snippet.** `Communication.on_update` calls `update_comment_in_doc`, which on v16 stores `[{"name": "<communication>"}]` only. Rows written by older versions may still hold `comment`/`by` text. | `hidden_copies.rewrite_comments_column` rewrites `_comments` to `{name}`-only entries on her records and on the records her matched Comments and Communications reference (for example the colleague's deal). |
| 4 | Table engines | `tabError Log` and `__global_search` are **MyISAM**. `tabVersion`, `tabEmail Queue`, `tabDeleted Document` and `tabWA Log` are InnoDB. | If the job rolls back, Error Log and search-index rows it deleted stay deleted (they were copies of her data). Tests clean MyISAM rows explicitly. |
| 5 | Global search queue | `update_global_search` only pushes a snapshot to the Redis list `global_search_queue`; `sync_global_search` writes it later (the scheduler runs it). The queue can still hold **snapshots of her records queued before the erasure**. | `post_commit.reindex_search` first drops queued entries for her records and any entry naming her identifiers, then re-indexes the scrubbed records and syncs. Without that step, the sync put her email back into `__global_search` (seen during testing). |
| 6 | Contact / Address naming | Contact is named "By script" from the full name (`Marisol Reyes`, `Marisol Reyes-1`, …). Address names also come from the address title (`Marisol Reyes-Billing`). | These primary keys keep her **name** after the erasure, and `Dynamic Link.link_name`, `CRM Deal.contact` and the match rows point at them. Outcome `docs` leaves out doctypes whose names hold data. Renaming is not in scope: see the phase 03 report. |
